# DraftDock 用户体验与可靠性审计

审计日期：2026-10-06。范围：读取本地 0.1.2 源码和已有测试，推演真实使用链路；本报告不把静态推演表述为已经执行的桌面交互测试。

## 真实工作场景

运营人员把 AI 生成的内容包保存到本机，内容包包括标题正文 MD、补充 TXT、图片子目录和 HTML。一次内容生产要投向公众号、小红书、X 和知乎，每个平台都需要独立标题、正文、图片顺序、适配结果和完成状态。工作台应支持“识别来源→保留母版→编辑平台稿→选择并排列交付图片→检查限制→输出发布包→记录发布状态”的连续链路。

## 用户建议与本轮范围

本轮优先解决会丢稿或误交付的链路：保存、历史、来源变化、目录模式、每个平台图片清单、交付包、统一正文处理、四平台资料和检查。不要把“自动适配”描述成自动完成高质量文案重写；确定性结构转换需要用户审核。

之后可建设：多个账号配置复用、模板管理、批量图片适配队列、跨篇搜索与状态筛选、发布后数据记录、HTML 来源候选预览、X 串文草稿、知乎回答场景、同步冲突检查。平台登录、自动发布和账号凭据管理应独立成后续项目，不能混入当前本地稿件交付实现。

## 验证要求

必须覆盖“编辑立即切平台”“编辑立即关闭”“损坏记录保存拒绝”“根 README 与多篇文章”“切源再恢复完整稿”“外部源变化保留编辑”“图片选择重启仍保持”“所选适配图进入发布包”。Windows 打包后验证页面渲染和预加载接口，不能仅以进程存活视为界面可用。所有测试使用临时素材或只读用户素材，不修改用户来源。

## 本轮二次复核

新加入 DraftBuffer 后补充了四项缓冲写入回归：快速跨文章/平台编辑、失败保留待写并重试、重叠 flush 串行、写入期间新增编辑。初版 flush 只遍历快照，单次 flush 在旧写入等待期间收到新输入仍提前返回；关闭确认据此存在丢最后输入的风险。该失败有确定测试复现，要求 flush 排空待写队列并在关闭保存期间锁定编辑。

图片生成的异步返回也应绑定生成开始时的文章和平台。若生成等待期间允许关闭适配窗口后切换文章，新返回的交付图不能把当前新文章的正文混写到原平台稿。人工刷新应先保存再采用磁盘最新记录；自动监听在首次未编辑稿的源文件变化后也应更新当前内容。
