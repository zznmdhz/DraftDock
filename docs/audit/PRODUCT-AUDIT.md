# 产品经理审计：从发布准备到多平台交付

审计日期：2026-10-06。依据为本轮优化前的 `src/renderer/src/App.tsx`、`src/main/library.ts`、`src/main/index.ts`、`src/main/outputs.ts` 与 README/PRD；本轮并行实施可能已修复部分问题。优先级按数据可靠性、实际发布阻塞和操作成本排序。

## 产品目标与关键缺口

目前产品解决了“找到素材、编辑正文、裁图”的一部分，但用户最终交付的是一套有标题、正文、图片顺序和发布入口的材料。代码中三个对象仍脱节：平台正文保存在 state，图片选择在 React Set 中，生成图在 manifest 中。真正的优化中心应是“同一篇内容在每个平台上的独立交付稿”，并把账号、选图顺序、派生图和发布状态绑定到该稿。

首要成功指标是：从打开已有图包到准备完整交付，用户能确定哪份文字、哪些图、什么顺序、给哪个平台，并且下次打开仍保持一致。发布端手工完成，因此本轮不需要自动登录或代发。

## 可证实问题与验收要求

| 优先级 | 证据与问题 | 对用户的影响 | 修改方向及验收 |

## 本轮可交付范围

1. 保存可靠性与历史恢复；自动/图包/文章库模式，来源变化提醒。
2. 公众号、小红书、X、知乎四种可扩展平台配置与发布前检查。公开规则标注来源、核对日期与适用入口；个性化预算明确区别于官方限制。
3. 平台独立图片选择、顺序、派生版本和状态。
4. 完整本地交付包与统一错误反馈，保留当前复制、拖图、DOCX能力。
5. 针对可靠保存、目录识别、限制校验、原图不改、图包完整性建立回归；打包后验证真实页面启动与 IPC。

## 后续规划而非本轮默认承诺

- X 串文与 Premium 长文、知乎问答：它们是独立发布形式，不能只换标签。
- 图片在正文中的精确插入与多图批处理：需要图文关系模型，不应把“附后图片”包装成完美排版。
- 多账号品牌模板、选题/排期与发布复盘：先验证人工记录实际被使用，再扩展成运营系统。
- 插件式平台适配器、规则版本迁移、海量素材缓存与增量监听。
- 授权平台 API 的草稿上传：需要逐平台权限和回执，保持人工发布确认；不以浏览器 Cookie 或模拟登录替代产品授权。

## 验收场景

- 新用户直接打开含多份 MD/TXT、HTML、子目录发布图片的图包，能看见正文候选和全部图片，HTML不误识别正文。
- 用户选择两份来源，编辑四个平台不同正文；输入后立刻切平台，返回和重启无丢字。
- 公众号选 3 张图，小红书选 5 张且重排，X选 4 张；任意切换后选择与顺序独立保持。
- X超长或超过4图时清楚提示，不能宣称材料通过；小红书未核实限制仅显示可改工作预算。
- 使用同一原图生成两次并选择其中一次交付；输出目录唯一、原文件哈希一致、manifest可追溯；错误图、跨平台派生或越界路径使交付失败且无半包。
- 发布后填写 URL 和状态，下次打开能辨识哪些平台已发；既不自动发布，也不把“导出成功”当成“发布成功”。
