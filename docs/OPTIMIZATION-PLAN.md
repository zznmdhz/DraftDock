# DraftDock 全面检查与优化修改文档

核验日期：2026-10-06。对象：当前本地 0.1.2 代码（包含上次尚未提交的图包/多来源/缩放修复），本轮先交付0.2.0，最终版本0.2.1 Windows补齐路径兼容。

## 1. 产品判断与目标

当前应用解决“找素材、裁图、复制正文”，但尚未形成可靠的多平台发布准备流程。核心改进方向是：同一篇内容保留原始素材，针对各平台维护独立工作稿、图片顺序与版本、账号工作预算，完成可追溯交付，并记录人工发布结果。

目标用户是使用 AI 生成 Markdown 和图片、同时运营公众号、小红书、X、知乎的个人或小团队。关键任务是将已有素材包整理成平台可用材料；本轮不引入自动改写服务或平台登录，以便先把本地链路做可靠。

## 2. 检查方法与证据

三个并行视角：专业产品审计、实际用户任务/代码可靠性审计、官方平台规则研究。分报告位于 [产品审计](audit/PRODUCT-AUDIT.md)、[用户审计](audit/USER-AUDIT.md)、[平台规则](audit/PLATFORM-RESEARCH.md)。来源包含 src/main、src/renderer、共享模型、测试和实际图包结构。代码能证明的缺陷与推测的用户需求分别标记；界面观感需用打包程序截图和真实交付文件核验。

## 3. 用户路径与主要不爽点

| 任务 | 当前问题 | 影响 | 目标行为 |
|---|---|---|---|
| 打开素材库 | 自动扫描碰到根 README 就合并所有子文件夹 | 文章混合，正文选错 | 明确“单篇图包/多篇文章库/自动”入口 |
| 选择正文 | 多文档取排序首份，来源更新不提醒，历史不可恢复 | 发布旧稿或丢编辑 | 可多选、显式重建、来源变更提醒、历史恢复 |
| 编辑多个平台 | 自动保存切换时被取消，缺少关闭保护 | 600ms 内输入可能丢失 | 改动立即进入内存缓冲，切换/关闭前落盘，失败可重试 |
| 配置图片 | 勾选重置、手柄不能排序、派生只取最新 | 输出顺序和平台版本不确定 | 每个平台保存勾选、顺序、所选交付版本 |
| 平台适配 | 只有两个硬编码平台 | X/知乎无法继续运营 | profile 统一格式、工作尺寸、入口说明、核验来源 |
| 发布前检查 | 无文本/图片检查 | 到后台才发现不合适 | 硬限制阻止交付、自定义预算提醒、未知规则明示 |
| 交付材料 | 正文/原图/裁图分离，DOCX默默跳过图 | 仍需手工拼包，可能少图 | 按顺序导出独立可追溯发布包，失败不能报成功 |
| 发布后运营 | 无账号/状态/URL记录 | 同一稿不知道发在哪 | 保存目标账号、工作状态、发布链接和备注 |
| 异常恢复 | 损坏 JSON 被吞后可能覆盖，坏目录拖垮扫描 | 工作稿损坏风险 | 不覆盖损坏状态、局部错误隔离、日志与重试入口 |

## 4. 平台标准化方案

统一实体：文章 → 原始正文/图片 → 平台工作稿 → 有序交付图片 → 发布前检查 → 交付目录 → 人工发布记录。

平台 profile 包含：平台 ID、发布入口/内容类型、正文格式、标题语义、计数字段、硬限制（若已核实）、推荐图像尺寸、官方来源 URL、核验日期、未知项。自定义账号工作预算单独保存，不能伪装成官方限制；账号名称仅用于本地标记，不代表已连接该账号。

| 平台 | 本轮入口 | 正文与图片处理 | 标准化边界 |
|---|---|---|---|
| 公众号 | 后台图文文章 | 保留富文本结构，独立标题，封面与正文图工作预设 | API限制不直接套到后台，富文本粘贴结果需后台确认 |
| 小红书 | 图文笔记 | 独立标题、纯文本配文、有序图集、3:4等工作预设 | 常见字数/张数不在未核实情况下硬编码 |
| X | 标准单条Post | 标题作为开头计入正文，twitter-text加权计数，有序图片 | 与Premium长文/串文分开，超长不静默截断 |
| 知乎 | 专栏文章 | 独立标题、富文本、图集及封面工作预设 | 回答入口属于不同模板，未核实限制保持未知 |

## 7. 质量与可衡量标准

- 零已知切换丢稿；任何保存失败在界面可见并能重试。
- 交付包中文本/图片顺序与当前选项一致，任何原素材SHA-256不变。
- 官方规则均带来源、核验日期、入口范围；未知上限不填假值。
- 所有阻塞问题在导出前可见；不能无声截断正文或跳过图片。
- 发布记录由用户手动设置，导出成功只说明材料已生成。
- 每项落地改动有测试或打包证据，未实现部分明确留在路线图。

## 8. 变更结果与验证记录

已实现并验证 O01–O10。第一次桌面回归在“输入后立即 window.close()”发现末尾输入未保存：Chromium先卸载页面，BrowserWindow关闭拦截不足。已增加preload beforeunload保活、保存确认后准许卸载，真实用户手势的桌面回归已通过（无手势的调试调用会被Chromium特殊处理，脚本已明确设置userGesture）。失败过程明确保留，不能以单元测试通过代替桌面验收。

截至本轮：8个测试文件、45项Vitest回归全部通过，Node/Renderer类型检查通过。包含真实junction/symlink、损坏状态保护、清空预算、外部删除派生文件等边界。测试中的不可写日志与TIFF警告为故意触发的失败容错场景，不代表运行白屏。

最终Windows x64包位于本地 `B:\Sync_AI\DraftDock\release\DraftDock-Setup-0.2.0-x64.exe` 和 `DraftDock-Portable-0.2.0-x64.exe`。没有卸载或覆盖你已有安装；运行新版安装包可升级。本轮所有原图包测试均复制到临时目录，未回写原素材。

打包程序验证：`node scripts/smoke-packaged.mjs` 启动页/preload/IPC/日志通过；传入真实图包时识别2份正文、10张图片，当前交付默认排除九图预览。`node scripts/smoke-workflow.mjs <打包exe> <真实图包>` 在真实副本加独立第二篇后通过根README隔离、立即平台切换保存、图片取消/排序持久化、缩小构图并从界面生成/选用新图、四平台完整交付、原素材SHA-256不变、来源历史恢复、立即重载与关闭保存。标准及1180×720视口的主要按钮均可达。

本机证据目录：完整打包工作流截图/日志位于 `C:\Users\lishu\AppData\Local\Temp\draftdock-workflow-JbZVLr`，真实图包启动/裁切截图位于 `draftdock-smoke-ix91Mb`，启动页位于 `draftdock-smoke-8q4BnL`。这些为本机临时证据，不上传包含素材内容的截图到公开仓库。脚本可复跑生成新的证据。

本轮明确未实现：真正多账号/账号默认模板、自动拆串文或长文、知乎回答、精确插图位置、批量队列、发布日历/指标和授权API。这些属于第6节后续范围，不把本地账号标记或素材导出等同于已完成账号运营系统。

云端补充回归：GitHub Windows runner的临时用户目录使用8.3短路径别名，原边界检查混用了lexical路径与realpath，导致合法图片被误拒。0.2.1将素材与来源匹配归一到真实路径，保留真正越界检查，并新增合法目录别名的生成、交付和来源回归。此问题不靠跳过测试或放宽安全边界处理。

已知兼容边界：DOCX支持基本标题、段落、列表与附后图片，不完整复刻Markdown表格/代码样式；HTML交付包作为结构化预览。平台后台粘贴和图片上传接受度仍需登录实际账号人工实测，本轮不会自动发布到你的账号。素材库移动后的绝对路径恢复仍需重新选来源和图片。
